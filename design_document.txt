Smart Campus Navigation and Facility Analytics System
Design Document

Course: CSCE 2110, Project 2
Author: Bobby Oliver
Updated: November 8, 2026


1. Purpose and scope

The program loads campus data from the instructor-supplied text files and lets
a user inspect and search facility records from a menu. This document covers
the facility module: loading with validation, listing, and the three searches
by ID, by name and by category.

The campus graph and the department tree are not implemented yet. Their menu
numbers are reserved and print a placeholder message, so the numbering will
not shift when those modules are added.

The source files, the four data files and this documentation sit together in
one flat project directory. The only subdirectory is testdata/collision, which
holds the small data set used to demonstrate a hash collision.


2. System overview

The program reads an optional data directory from the command line and falls
back to the current directory when none is given. It then reads buildings.txt
into a vector of names, and the facility database reads facilities.txt,
checking each record against that building list and inserting accepted IDs
into the hash table. A menu loop then prints the options, reads one line of
input, carries out the chosen operation and repeats until the user enters 0.

main.cpp is the entry point. It holds the building loader, the menu and the
dispatch to each operation. Facility.h defines the record itself.
FacilityDatabase.h and FacilityDatabase.cpp hold the accepted facilities, the
file loading, the listing and the searches. HashTable.h and HashTable.cpp are
the custom ID table. Utils.h and Utils.cpp hold the small helpers: trimming,
case conversion, field splitting, the ID format check, path joining, and
blank or comment detection.


3. Data structures

A Facility holds four strings. The ID is stored uppercase, the name may repeat
between records, the building spelling is copied from buildings.txt, and the
category keeps the spelling of the record that was accepted. A default
constructor lets a Facility act as an empty search result and lets facilities
live in a vector.

FacilityDatabase keeps two structures side by side: a vector of accepted
facilities in file order, and the hash table keyed by ID. The vector exists
because facilities must be listed in file order, which a hash table cannot
promise. The table exists because an ID lookup must not scan the whole
collection.

The HashTable holds a vector of buckets, where each bucket is itself a vector
of facilities, along with the capacity, the number of entries and the number
of collisions. Separate chaining was chosen over open addressing because a
chain can keep growing, so the table never needs resizing and there is no
fixed maximum number of facilities.

main.cpp keeps the accepted building names in a vector of strings, in file
order. Facilities are validated against that list, and the stored spelling is
copied into each accepted facility, so a different capitalization in
facilities.txt never reaches the output.

No std::map, std::unordered_map, std::unordered_set or std::hash appears
anywhere in the project.


4. Hash table design

The hash function starts an index at 0 and, for each character c of the
uppercase key, replaces it with (index * 31 + c) % capacity. Uppercasing
first means F004 and f004 always reach the same bucket. Taking the remainder
at every step keeps the running value small enough that it cannot overflow.
The multiplier 31 is the usual small prime for string hashing and spreads
similar keys such as F001 and F002 across different buckets.

A collision is counted when an accepted insertion lands in a bucket that
already holds at least one entry. Duplicate detection runs before the count is
taken, so a rejected duplicate ID never changes it. This keeps the diagnostic
consistent with the number of records actually stored.

The supplied data reports capacity 11, entries 10 and one collision, because
F009 and F010 both hash to bucket 0. My own test data in testdata/collision
reports capacity 11, entries 5 and two collisions, where F004 and F100 share
bucket 6 and F009 and F010 share bucket 0.

Insertion works in four steps: compute the bucket from the uppercase ID, scan
that bucket and return false if the ID is already there, add one to the
collision count when the bucket was not empty, then store a copy with an
uppercase ID, add one to the entry count and return true.

Lookup works in two steps: compute the bucket from the uppercase ID, then scan
only that bucket for the record. A lookup never touches another bucket or the
facility vector.

The diagnostic method returns text such as "hash capacity 11, entries 10,
collisions 1", which is appended to the facilities load summary line.


5. File loading and validation

The files are read in the required order: buildings.txt, connections.txt,
facilities.txt, departments.txt. Buildings must come before facilities because
facility records are checked against the accepted building names.
connections.txt and departments.txt are listed for completeness but are not
read yet, since the graph and tree modules are still pending.

Every loader follows the same line rules. A UTF-8 byte order mark on the first
line is stripped. Blank lines are skipped. A line whose first non-whitespace
character is # is a comment and is skipped, while a # anywhere else is
ordinary text, so a name like Room #5 is valid. Leading and trailing
whitespace, including the carriage return left behind by Windows line
endings, is trimmed from every field. Skipped lines count as neither accepted
nor rejected.

buildings.txt holds one name per line. A name is rejected when it is empty
after trimming, when it contains the field separator | so that no other file
could reference it, or when the same name ignoring case was already accepted.
The first spelling seen is kept and later duplicates are rejected.

facilities.txt holds one record per line, with the ID, name, building and
category separated by |. The checks run in a fixed order and the first
failure decides the warning: exactly four fields, no field empty after
trimming, an ID of F followed by exactly three digits after trimming and
uppercasing, a building that exists in buildings.txt ignoring case, and an ID
not already used by an accepted record. On success the record goes into both
the vector and the table. On failure a warning names the file, the line number
and the reason, and the line counts as rejected. A duplicate ID keeps the
first record and never overwrites it.

Each file ends with one summary line, for example "buildings.txt: 7 accepted,
0 rejected" or "facilities.txt: 10 accepted, 0 rejected (hash capacity 11,
entries 10, collisions 1)". Every number is computed from the data.

A file that cannot be opened prints an error naming the file, is treated as
empty, and the program continues. A file that opens but holds no records
behaves the same way without the error message.


6. Search behaviour

An ID search, menu option 2, trims and uppercases the input before validating
it, then reports one of three things. Invalid input prints "Invalid format: an
ID is F followed by exactly three digits." A valid ID that is absent prints
"Not found: no facility with ID F999". A hit prints the name, building and
category on one line. The lookup goes through the hash table and never
through a scan of the facility vector.

A name search, menu option 3, trims the input and compares it to each facility
name ignoring case. Names are not unique, so every match is printed in file
order followed by the count, as in "2 facilities found with name: Room 101".
A single match uses the singular wording. A miss prints "No facilities found
with name: ..." and a blank value prints "Invalid input: please enter a
facility name."

A category search, menu option 4, behaves the same way against the category
field, with the word category in place of name.

The name and category searches are linear scans. Neither field is unique, so a
hash table would add complexity without improving correctness.


7. Complexity

Loading n facilities is linear in the number of records, with an extra
quadratic cost from checking each facility building against the building list.
An ID search is constant time on average and at worst the length of one chain.
Name and category searches are linear, as is listing every facility. A hash
insertion is constant time on average.

With eleven buckets and ten records the longest chain is two, so lookups in
the supplied data cost at most two comparisons.
